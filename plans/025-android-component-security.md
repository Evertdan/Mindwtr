## Findings

1. **SEC-02 alarm receivers exported** — generated manifest has `com.emekalites.react.alarm.notification.AlarmReceiver` and `AlarmDismissReceiver` `exported="true"` with no permission (verified in generated AndroidManifest.xml:76,83): any app can cancel every reminder (small sequential AlarmIds) or fire stored alarms early. FIX in `plugins/android-manifest-fixes.js`: set both to `exported="false"`. Our own action buttons use `PendingIntent.getBroadcast` (creator identity) and keep working; `AlarmBootReceiver` STAYS exported (protected BOOT_COMPLETED). Red test: extend `plugins/android-manifest-fixes.test.js` asserting the two receivers get exported=false and boot receiver untouched (fails today).
2. **SEC-01 notification-open payload trusts any caller** — MainActivity (generated by `plugins/android-startup-trace.js`) calls `cacheNotificationOpenPayload(intent)` on every onCreate, copying `taskId`/`actionIdentifier` from caller extras; `apps/mobile/hooks/root-layout/use-root-layout-notification-open-handler.ts:74` then completes the task. Any installed app can mark arbitrary (UUID-known) tasks done. FIX in the generated Kotlin: drop the payload unless `referrer?.host == packageName` (self-launched PendingIntents satisfy this). Red test: plugin test asserting the generated MainActivity source contains the referrer guard; plus keep the existing happy-path behavior (notification taps still work — the guard must use the activity referrer, not intent extras).
3. **SEC-03 ContextAutomationReceiver open to all** — `plugins/android-manifest-fixes.js:93` exports it with no permission; `modules/context-automation/.../ContextAutomationReceiver.kt:20` wakes a headless task doing a full `fetchData()` (`lib/context-automation-headless-task.ts:71`); dedupe keyed `action:context` (`lib/context-automation-handler.ts:13`) is defeated by varying the context. FIX: declare a `protectionLevel="normal"` custom permission in the manifest plugin and set `android:permission` on the receiver (Tasker-class automation apps can request a normal permission — document the permission name in the plugin comment); make the dedupe a global rate limit (e.g. max N headless starts per minute regardless of key). Red tests: manifest plugin test for the permission; `context-automation-handler.test.ts` (TEST-14) driving TTL + global limit with injected nowMs; parser table test over `parseContextAutomationHeadlessTaskData` (url branch, action aliases, malformed extras).
4. **SEC-17 backup rules structural trap** — generated manifest points at expo-secure-store's rules: `<include domain="sharedpref" path="."/>` + exclude SecureStore. Exhaustive-include means DB/attachments are excluded today, but every future SharedPreferences file is silently enrolled in Google cloud backup. FIX: ship app-owned `backup_rules.xml`/`data_extraction_rules.xml` that include nothing (the store has its own transport), wired via the manifest plugin; keep `allowBackup` semantics unchanged otherwise. Red test: plugin test asserting the manifest references the app-owned rules and the rules files include nothing.
