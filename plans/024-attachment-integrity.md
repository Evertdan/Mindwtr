## Findings

1. **SEC-05 mobile never validates attachment bytes; malformed fileHash disables validation** — `packages/core/src/attachment-hash.ts:11` returns null without `crypto.subtle`; Hermes has none (`apps/mobile/lib/sync-crypto-native.ts:1`, no polyfill); nulls swallowed at `attachment-transfer.ts:42,246-249` and `apps/mobile/lib/attachment-sync-utils.ts:541`. Also `attachment-transfer.ts:40` skips validation when `expected.length !== 64`, and `sync-normalization.ts:101-111` never sanitizes `fileHash`. FIX (three parts, one finding): (a) pluggable digest in core (reuse the existing native-module seam pattern from sync-crypto; register a `sha256` provider at mobile startup using the same native crypto module MWENC1 uses — check `sync-crypto-native.ts` for what is available before adding any dependency; STOP if a new native dependency would be required); (b) fail closed: when a syntactically valid 64-hex `fileHash` is expected and bytes mismatch OR no digest is computable, treat as validation failure (bounded, terminal per P8), never silent-skip; (c) drop malformed `fileHash` to undefined at the sync-merge boundary beside `cloudKey`. Red tests: TEST-08 file (`attachment-hash.test.ts`: digest correctness + subtle-absent branch) plus transfer tests for match/mismatch/short/null.
2. **SEC-04 unbounded download allocation** — `packages/core/src/http-utils.ts:231` allocates `new Uint8Array(total)` from Content-Length; uncapped `res.arrayBuffer()` fallbacks at `webdav.ts:693`, `cloud.ts:365`; desktop reads whole attachment at `sync-attachment-backends.ts:508-527`. FIX: reject before reading when content-length exceeds a cap (choose cap ≥ `DEFAULT_MAX_FILE_SIZE_BYTES` from attachment-validation.ts:21 with headroom for the sync document itself — pick 2× the upload cap and document why), count bytes while streaming so a lying/absent header aborts, allocate incrementally. Red test: fake response with huge content-length → typed error, no allocation.
3. **SEC-07 upload source containment** — `attachment-transfer.ts:222-241` uploads from `attachment.uri` verbatim; absolute paths pass the merge sanitizer; a hostile sync document can exfiltrate arbitrary local files on next sync. FIX: optional `canUploadFrom(path)` on `AttachmentTransferLifecycleOptions`, default supplied by each platform = managed attachments dir + the configured sync folder + (desktop) paths the user explicitly attached this session; failing attachments refresh `localStatus` but are never read. CAUTION (#1038): relocated-profile/linked attachments legitimately live outside the managed dir on DESKTOP — desktop's predicate must allow the user-chosen linked paths recorded in the attachment itself ONLY when the attachment was created locally (has localStatus history), not when it arrived over sync with no local provenance. If clean provenance distinction proves impossible, STOP and report the options instead of shipping a guess.
4. **SEC-08 sanitize restore/import + local_api cloudKey** — `backup-transfer.ts:296` (`prepareRestoredBackupDataForSync`) and `import-runner.ts:125` (`filterAdditiveBackupAttachments`) never call `normalizeAttachmentsForSyncMerge`; `local_api.rs:3240` accepts any string cloudKey; `sync-service-utils.ts:270` `resolveFileBackendPath` keeps `..`. FIX: call the normalizer at both entry points; enforce `ATTACHMENT_CLOUD_KEY_PATTERN` in `valid_attachments`; reject `..` segments in resolveFileBackendPath. Red tests each.
5. **BUG-16 fileHash stranding + permanent rehash loop** — `attachment-transfer.ts:246-249` backfills fileHash only in the never-again first-upload branch; `:294-298` changed-but-unhashable does nothing (no stat update) → every cycle rereads up to 50MB per attachment on mobile. FIX: move the missing-fileHash backfill into the check-on-touch block; when content changed but hash unavailable, record the observed stat device-locally (marker) so re-hash waits for the stat to move — do NOT publish a fileHash you could not compute. Red test: stat-changed + hash-null cycle runs once, second cycle skips.
6. **BUG-24 cleanup reference-set encoding asymmetry** — `attachment-cleanup.ts:103-119,138-139` raw string equality; mobile checks both encodings (`sync-attachment-cleanup.ts:71-75` proves both arrive); cloudKey inserted raw at `:119` but looked up sanitized at `:266,300`. FIX: guarded decodeURIComponent + separator normalization in `normalizeAttachmentCleanupUri`; run the cloudKey sanitizer when populating the live set. Widening the protect-set fails safe. Red test: two encodings of one uri protect each other.
7. **BUG-26 desktop transfer pass has no freshness checkpoint** — `apps/desktop/src/lib/sync-attachments.ts:16-25` Omits `beforeEachAttachment` and hardcodes `maybeYield` (no `ensureLocalSnapshotFresh`), unlike cleanup (`sync-attachment-cleanup.ts:204`). FIRST INVESTIGATE: does the enclosing core SyncRun re-check freshness before persisting the mutated clone (trace `sync-run.ts` attachment phase → persist)? If yes, downgrade to wasted-work and only add the checkpoint for early abort; if no, this is a lost-edit race and the fix is required. FIX: stop Omitting, compose caller guard with maybeYield, invoke before the check-on-touch transfer too. Red test at the desktop seam with a snapshot invalidated mid-pass → LocalSyncAbort + requeue (mirror the cleanup lifecycle's test).
8. **TEST-01 mobile attachment suite tests a hand-copy** — `apps/mobile/lib/attachment-sync.test.ts:81-186` vi.hoisted reimplementation of the lifecycle, mocked WITHOUT importActual (`:202`), missing all of #1057; `computeSha256Hex` pinned null. FIX: `vi.mock('@mindwtr/core', async (io) => ({...await io(), <network stubs only>}))`, delete the copies, add per-backend tests: stat/hash mismatch re-uploads in phase 'prepare' and re-downloads in 'post-merge'. Expect fallout: the real lifecycle calls stat/hash hooks the fs mock must now answer.
9. **TEST-10 ensureAttachmentAvailable coverage** — new `apps/mobile/lib/attachment-sync-availability.test.ts`: one happy path per backend branch (`attachment-sync-availability.ts:110,119,141,170`), hash-mismatch leaves `localStatus !== 'available'` and writes nothing, two concurrent calls → one fetch (downloadLocks `:40,236`).
