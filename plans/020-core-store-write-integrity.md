## Findings (each = its own red test + fix + commit)

1. **BUG-06 partial-snapshot guard is length-blind** — `packages/core/src/store-helpers.ts:637` `assertCollectionSnapshotIncludesExistingItems` returns early when `nextItems.length >= previousItems.length` (verified verbatim). A snapshot dropping N rows while adding N new ones passes. Fix: drop the length short-circuit; always build the id set (keep a `nextItems === previousItems` identity fast path if perf demands). Red test: same-length snapshot missing one existing id must throw "Refusing to save a partial … snapshot". Watch `bun run test:perf` afterwards (this runs on every save).
2. **BUG-05 imported reference tasks keep date/recurrence fields** — `packages/core/src/import-apply.ts:451-479` builds the Task literal without `getReferenceTaskFieldClears()` (`store-helpers.ts:42-58`) although importers can emit `status:'reference'` with dueDate/recurrence/priority set (omnifocus-import.ts:320, mindwtr-csv-import.ts:142,508). First later edit silently wipes those fields (store-helpers.ts:134-140). Fix: spread the clears when resolved status is `reference`. Red test: import a reference task with a dueDate → stored task has no dueDate (matches what addTasks does, store-tasks.ts:441-443).
3. **BUG-09 date-only branch accepts calendar-invalid dates** — `packages/core/src/date.ts:698-715` builds `new Date(year, month, day…)` and checks only `isValid`, so `2024-02-31` → March 2. The `isValidCalendarDate` helper already exists at `date.ts:673-677` (added this window for the ISO fast path). Fix: call it in the date-only/local branch; return null on failure. Red test: `safeParseDate('2024-02-31')` → null (fails today).
4. **BUG-10 duplicateTask leaks focusOrder + archive metadata** — `packages/core/src/store-tasks.ts:855-879` sets `isFocusedToday:false` but keeps `focusOrder` (synced field! `sync-signatures.ts`) and the four `*BeforeProjectArchive`/`projectArchivedAt` fields. Fix: clear all five beside the existing `isFocusedToday:false`. Red test: duplicate a focused task → copy has `focusOrder === undefined`.
5. **BUG-11 recurring follow-up gets no project order** — `packages/core/src/recurrence.ts:1858-1888` omits `order`/`orderNum`/`pushCount`; every sibling creation path reserves one (`store-tasks.ts:404,445-447` addTasks; `:848-851` duplicateTask; `compareTasksByProjectOrder` sorts missing as +Infinity). Fix at the store integration site (`applyTaskUpdates` call sites that append the follow-up), mirroring duplicateTask's `createProjectOrderReserver`; default `pushCount: 0`. Red test: complete a recurring task inside a project → follow-up keeps a finite order near the original, not bottom-of-list. NOTE the recurrence guardrail: run the full recurrence matrix suite after (`bun run --filter @mindwtr/core test -- recurrence`).
6. **BUG-19 saveTask drops the snapshot param** — `packages/core/src/storage.ts:34` declares `saveTask?(task, snapshot?)`; `sqlite-adapter.ts:1036` ignores `snapshot`, so a deviceId minted inside `updateTask` (`store-tasks.ts:602-605,638`) never persists on the incremental path → next launch mints another, churning revBy. Fix: persist `snapshot.settings` inside saveTask's transaction when provided (or force the full-snapshot path when deviceState.updated). Red test: adapter-level — saveTask with a snapshot carrying a new deviceId → settings row updated.
7. **BUG-18 store discards incremental visible/byId maintenance** — `packages/core/src/store.ts:294-296` (verified verbatim) unconditionally recomputes `record[visibleKey]`/`record[mapKey]` from `_allTasks`, so the incremental updates produced at `store-tasks.ts:256-258,275-277,598-601,610-612,882,993,1139,1149` are dead weight. DECISION (fixed): keep `prepareStoreStateUpdate` as the single derivation site and DELETE the producers' incremental `tasks`/`_tasksById` keys and now-dead helpers. Risk: `applyVisibleTaskChanges` appended newly-visible rows at the end while `selectVisibleTasks` preserves `_allTasks` order — the surviving behavior is the CURRENT observed one (derivation always won), so list-order tests should not change; if any does, that test was pinning dead code — STOP and report instead of adjusting behavior. Verify with the perf suite (`bun run test:perf`) that removing producer work doesn't regress (it should slightly improve).
8. **BUG-20 one malformed row bricks every launch** — `packages/core/src/store-load-migrations.ts:685-697` runs 18 migrations with no per-migration isolation; unguarded dereferences at `:531-542,555-601`; outer catch (`store-settings.ts:442-450`) leaves the store empty forever. Fix: wrap each `migration.run` in try/catch, `logWarn` with migration name, continue with pre-migration state. Red test: inject a null element that makes one migration throw → load completes, other migrations applied, warning logged. Guardrail note: loading never mutates data — the isolation must not change what successful migrations write.
9. **TEST-11 sync-merge-settings direct coverage** — `sync-merge-settings.test.ts` is 72 lines for a 673-line module. Add table-driven tests per SettingsSyncGroup: incoming-newer / local-newer / local-opted-out / one-side-empty, plus a `sanitizeMergedSettingsForSync` round-trip. While writing them, verify two suspicious behaviors and REPORT (do not change without evidence): `:563-565` reads pre-merge `localSettings.syncPreferences` rather than merged prefs; `isSameValue` uses key-order-sensitive JSON.stringify. Commit as `test(core): cover sync-merge-settings group arbitration`.
